QuickBite architecture

QuickBite has no backend server. The phone talks to Gemini Live directly, runs every tool call itself and writes each result to Cloud Firestore. The responder console listens to Firestore, so a fact Mia hears appears on the console within seconds. Recordings, mail, maps and live video use free services around that core.

System overview

The six flows

  1. 1
    Live sessionA WebSocket to Gemini Live. The mic and camera frames go up; Mia’s voice and tool calls come down; tool results and known facts go back up.
  2. 2
    After the callCase summary, bulletin and redaction (3.5 Flash-Lite), then case linking (3.1 Flash-Lite).
  3. 3
    Shared incident clientEach tool result is written to Firestore as it arrives. Listeners bring responder messages and routes back to the phone.
  4. 4
    Realtime syncThe console listens to the incidents; acknowledge, notes, messages and routes are written back.
  5. 5
    ServicesLocation and routing, Drive recordings, and the case-report and alert mail.
  6. 6
    Live mediaCamera and mic stream one way, peer to peer, from the phone to the console.

A live call, step by step

The incident exists in Firestore and rings on the console before Gemini says a word. After that, every answer the caller gives becomes a tool call that the phone writes straight to Firestore, so responders read the situation while the call is still going.

The Gemini agent loop

Mia does not chat. Everything she learns leaves the session as a function call. The phone executes it, writes it to Firestore, and puts what is now known into the next tool response, so Mia never asks for something she already has.

Key pool · metering

Right-sized and metered

Each task uses the smallest model that does the job. The free-tier key is tried first and the paid key takes over on a quota error, per model. Tokens per task are recorded on every incident.

Data and security

Firestore is both the database and the realtime channel, and its security rules do the job a server would: every write is validated against a fixed schema and allowed transitions.

What the rules guarantee

  • Only known fields, with allowed values and size limits, can be written.
  • Status only moves forward (new → acknowledged → in progress → resolved), and an ended call never goes live again.
  • Start time, way in and caller device id never change after creation.
  • Notes, the stress trend, the reasoning and the transcript can only grow.
  • Status, notes, acknowledgement, viewed, outcome and credibility can be changed only by an active responder.
  • Incidents, messages, snaps and recordings can never be deleted.
